How it works, end to end

A quiet desk for DSA practice, on your own computer.

Carrel is one Go binary. It starts a small server on 127.0.0.1, opens your browser, compiles your Java or C++ with the compilers you already have, and keeps every solution as a plain file in ~/.carrel. No account, no cloud, no Docker.

01 · The big picture

Three places: your browser, the binary, your disk

The browser only draws the screen. Everything that touches files, compilers or the network happens inside the Go binary, behind one guard. Click any box to see what it does.

02 · Start-up · main.go

What happens when you type carrel

Start-up takes tens of milliseconds. The web UI and all 183 problem packs are already inside the binary through go:embed, so there is nothing to unpack or download.

  1. Read flags. --port (default 7777) and --no-open. The words version, doctor, export and import run a subcommand instead and exit.
  2. Find the data folder. config.Home() uses $CARREL_HOME if set, otherwise ~/.carrel, created with mode 0700. An old ~/.dsa folder from the earlier name is moved over once.
  3. Load problems. problems.Load(Builtin(), ~/.carrel/packs). Later sources override earlier ones, so your own pack can replace a built-in one with the same id.
  4. Build the server. server.New opens the store (creates solutions/) and reads config.json. A damaged config falls back to defaults so practice is never blocked.
  5. Listen on loopback only. net.Listen("tcp", "127.0.0.1:7777"). If 7777 is busy it asks the OS for any free port. SetAddr then records the exact host names the guard will accept.
  6. Open the browser. 50 ms later: xdg-open on Linux, open on macOS, rundll32 url.dll on Windows.
  7. Serve. A plain http.Server with a 5 second header timeout serves the API and the embedded UI until you press Ctrl+C.
// main.go, trimmed
home, _ := config.Home()
lib, _ := problems.Load(problems.Builtin(),
    os.DirFS(filepath.Join(home, "packs")))
srv, _ := server.New(home, lib)

ln, _ := listen(*port)        // 127.0.0.1 only
srv.SetAddr(ln.Addr().String())

go func() {
    time.Sleep(50 * time.Millisecond)
    openBrowser(url)
}()
httpSrv := &http.Server{
    Handler:           srv.Handler(),
    ReadHeaderTimeout: 5 * time.Second,
}
httpSrv.Serve(ln)

04 · internal/runner

Compile once, run every case in one process

Starting a JVM for each of 60 cases would be slow. So every problem has a small driver that reads all cases from stdin and prints exactly one line per case, flushing after each one. Because of that flush, the runner always knows which case a crash happened on, and can restart from the next one.

The driver protocol

  • stdin: a line with T, then T cases, each in the problem's own text format.
  • stdout: exactly one line per case. A case that throws prints ERROR <message>.
  • Your own prints go to stderr (Java swaps System.out, C++ swaps cout's buffer), so debug output never breaks results.
  • Java: you write class Solution, the driver is Main.java. C++: you write free functions in solution.cpp, which driver.cpp includes.
  • Output is compared after trimming spaces: got == expected.

The exact commands

# Java, in a fresh temp folder carrel-run-*
javac -d out Solution.java Main.java
java -Xss64m -Xmx256m -XX:+UseSerialGC -cp out Main

# C++ (Unix: memory capped through the shell)
g++ -O2 -std=c++17 -o prog driver.cpp
sh -c 'ulimit -v 1048576; exec "$0" "$@"' ./prog

Limits and what they report

When several things go wrong, one wins in this order: timeout, too much output, memory, crash, ok. Crash notes come from how the process ended: signal 11 is a segmentation fault, 8 a division by zero, 6 an abort, 9 often means out of memory. A Java StackOverflowError arrives as an ERROR line and gets its own note.

The runner also watches stdout while it arrives. At the first OutOfMemoryError or bad_alloc it stops the process, because the driver would otherwise catch it and run out again on every later case.

05 · internal/store

How your code is saved

Every keystroke restarts a 600 ms timer in the browser. When you stop typing, one PUT /api/solution goes out, and the server writes a plain file. Running or submitting saves too, so you never lose the version you tested.

pair-with-target-sum · JavaSaved on this computer
debounce timer600 ms

Requests the browser sent, newest first

On the server, a save is four checks and a rename

  1. Guard. Host must be our loopback address, and the request must carry X-Carrel: 1.
  2. Decode. JSON body {problem, lang, code}, at most 1 MB.
  3. Validate. The problem must exist in the library, the id must match ^[a-z0-9][a-z0-9-]{0,63}$, and the language must be java or cpp. Only then is a path built, so no request can reach outside the folder.
  4. Write atomically. Write <id>.java.tmp with mode 0600, then os.Rename it over the real file. A crash halfway leaves the old file whole.
func (s *Store) Save(id, lang, code string) error {
    p, err := s.path(id, lang) // validates id and lang
    if err != nil { return err }
    tmp := p + ".tmp"
    if err := os.WriteFile(tmp, []byte(code), 0o600); err != nil {
        return err
    }
    return os.Rename(tmp, p)
}

│ └─ lru-cache.java one per problem and language

Opening a problem is the reverse: GET /api/problems/{id}?lang=java returns your saved file if there is one, otherwise the pack's starter.java, plus saved: true|false. If a save fails the badge turns to "Not saved" with a retry button.

Because they are ordinary files, you can open them in any editor, commit them to git, or move them with carrel export and carrel import.

06 · Progress and the learning path

Tried, solved, and when to come back

After every run the server marks the problem. A submit where every case passed marks it solved; anything else marks it tried. Solved is never downgraded. Compile errors do not count as an attempt.

Spaced reviews

The first solve schedules a review 3 days later. Solving again once it is due moves on to 10 days, then 30, then never again. Solving early changes nothing. Reviews show only when "Remind me to review" is on, but the dates are always kept.

What to practise next: GET /api/next

Problems link to each other with buildsOn and leadsTo. The server picks one suggestion by trying these rules in order and stops at the first that matches. Nothing is ever locked.

leadsYou just solved something: the first problem it leads to whose prerequisites are all solved.
continueThe problem you tried most recently in this sheet.
readyThe first unsolved problem whose prerequisites are all solved.
anyThe first unsolved problem in sheet order.
404Every problem in the sheet is solved.

Two sheets: Patterns teaches one technique per group, and Real interviews uses those techniques in realistic tasks, each linked back into the patterns sheet.

07 · internal/testgen

Fresh tests on every submit

Nothing large is stored. Each problem names a generator, and on submit the server draws a seed between 1 and 1,000,000 and asks for 50 cases. The same seed always gives the same cases, and the seed is shown in the result, so a failure can be reproduced.

Case sizes for one submit

Height is the input size on a log scale, computed by the same sizeFor rule as the Go code.

25 small, 2 to 11 20 medium, 20 to 319 5 large, 2000 to 9999 
// a generator plants or computes the answer
type Generator func(rng *rand.Rand, size int) Case

func Generate(name string, seed int64, n int) ([]Case, error) {
    g := registry[name]
    rng := rand.New(rand.NewSource(seed))
    for i := 0; i < n; i++ {
        out = append(out, g(rng, sizeFor(i, n)))
    }
    return out, nil
}
  • 183 generators are registered by name, one per problem.
  • Each one either plants a known answer or computes it with a reference solution in Go.
  • Every generator has a Go test that recomputes the answer by brute force.
  • Large cases (up to about 10,000 elements, or deep chains in tree problems) catch slow or recursive-only solutions.

A submit is three kinds of case

examples shown in the statement · edge fixed, hidden unless failing · random 50 from the seed

Two checks keep every pack honest

go test ./internal/problems

problems.Validate checks every built-in pack: valid difficulty and sheet, a registered generator, a ## Constraints heading, enough examples and edge cases, clean input text, links that exist both ways, and no buildsOn cycles. Real-interview problems also need a ## Follow-up heading.

make check-packs

cmd/packcheck runs the reference solutions in tools/refs/<id>/ through the real runner, in both languages, on the examples, edge cases and 200 random cases from seed 1. Every case must pass. References live outside internal/, so they never ship in the binary.

Input formats are shared across packs: arrays as n then values, trees in level order with null, graphs as n m then edges, grids as rows cols then rows, and design problems as a list of calls.

09 · Local safety

A server that runs code must not take orders from other sites

Any web page you visit could try to send requests to 127.0.0.1:7777. Carrel stops that in layers, before a single file or compiler is touched.

Loopback onlylistens on 127.0.0.1, never on the network
Host checkmust be 127.0.0.1:port or localhost:port, which stops DNS rebinding
X-Carrel: 1required on every write; other sites cannot add it
Validationknown problem id, java or cpp, known mode
Size limits1 MB JSON, 20 MB zip, 16 MB output
Files0600 files, 0700 folder, key never sent back
your tab · POST /api/run
another site · POST /api/run

The guard

One middleware wraps every route. It checks the Host header against the allowlist set by SetAddr, demands X-Carrel on anything that is not GET or HEAD, and marks every API answer Cache-Control: no-store.

The API key

Stored only in config.json with owner-only permissions. GET /api/config returns hasKey: true, never the key. Errors from providers are scrubbed twice so the key cannot leak into the page.

Zip import

Entry names are never used as paths. Only progress.json and solutions/<id>.java|cpp are accepted. Links, folders, .., absolute paths and backslashes are rejected, and the whole zip is checked before anything is written.

Your own code is not sandboxed beyond the time and memory limits. That is the same as running it yourself, which is exactly what Carrel does.

How "Explain only" is enforced

Asking the model nicely is not enough, so the server checks the answer itself.

  1. Ask with a tutor system prompt: explain concepts, point out what is wrong, one hint at a time.
  2. Scan the reply for fenced code blocks longer than 12 lines.
  3. Ask once more if one is found: "Your last answer contained too much code."
  4. Strip any long block still left, replacing it with [Code removed because Explain only is on.]

Turn Explain only off and the reply passes through untouched. Interview mode hides AI help entirely, along with hints, and starts a timer.

11 · internal/server

The whole API, 13 routes

JSON in, JSON out, built on Go 1.22's method-aware http.ServeMux. The UI calls these through one small api() helper that always adds X-Carrel: 1.

The browser side

  • A single app.js with a hash router: #/ sheets, #/p/<id> practice, #/settings.
  • DOM is built with a tiny el() helper and textContent, never innerHTML with problem or user text.
  • The editor is CodeMirror 6, bundled once into web/vendor/editor.js and committed, so building Carrel never needs Node.
  • Results appear as a grid of squares revealed over about a second; click one to see input, expected and got.
  • Two themes, Paper and Ink, five accents, a focus layout, interview mode, and keyboard keys to move between problems.

13 · Build, release, install

From a merged pull request to your machine

PR merged→ CI: gofmt, vet, test, check-packs→ Release Drafter updates the draft→ Owner publishes→ make dist: 5 archives + checksums→ install.sh verifies sha256→ ~/.local/bin/carrel 
make build        # builds ./carrel
make test         # go test ./...
make vet          # go vet ./...
make check-packs  # references pass every pack
make site         # website into site/dist
make dist         # release archives

./carrel doctor
CARREL_HOME=/tmp/c ./carrel --no-open --port 7777
  • Archives: linux and darwin for amd64 and arm64 as .tar.gz, windows amd64 as .zip, each built with CGO_ENABLED=0 -trimpath and the version stamped in.
  • Install script: detects OS and CPU, downloads the archive and checksums.txt, refuses to install if the sha256 does not match, then installs to ~/.local/bin. No admin rights needed.
  • CI: Go 1.22 and stable, Temurin 21 and g++, so the runner tests use real compilers.

Known limits

  • No C++ memory limit on Windows yet.
  • C++ printf bypasses the redirect and can break your own results.
  • Each run compiles in a fresh temp folder; nothing is cached.
